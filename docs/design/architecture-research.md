# Architecture: research

This note collects what primary sources say about structuring a VS Code extension like Proxy Toggler,
and about the design vocabulary the architecture review uses (module, interface, depth, seam, adapter,
leverage, locality). One read-only research pass ran on 2026-10-27. It checked VS Code's API documentation
and `vscode.d.ts` at 1.97.0 (the minimum engine) and 1.143.1 (the latest stable release, published
2026-10-22), the source of five Microsoft extensions at tagged releases, and the authors' own texts for
the design terms. Every claim cites its source; source code is cited at a tag or commit with line numbers.
How VS Code, Electron and `@vscode/proxy-agent` resolve proxies is not repeated here: see
[the v0.2.0 research](v0.2.0-research.md).

**Method.** VS Code documentation was read from `microsoft/vscode-docs` at commit
[`da21355`](https://github.com/microsoft/vscode-docs/tree/da213552439825628e0ab958dbde1e413dbc36bf)
(2026-10-26), the source of code.visualstudio.com; the Testing Extensions page was also checked live on
code.visualstudio.com. `vscode.d.ts` and extension sources were fetched with `gh api` at the tags named.
Context7 (`/websites/code_visualstudio_api`) was used to find pages and agreed with the source text. The
Microsoft Learn MCP server returned no VS Code extension pages, as `QUALITY_BASELINE.md` also records.
Ousterhout's book was read through the 20-page extract he publishes on his Stanford page, plus his
CS 190 lecture notes and his written debate with Robert Martin; chapters outside the extract were not
read (see [Items marked UNVERIFIED](#items-marked-unverified)). Line numbers for this repository's files
refer to the working tree on 2026-10-27: commit `db2ec08` on `feat/v0.2.0-profiles` plus uncommitted
changes. No repository file other than this one was changed.

**Versions.** The latest stable release is 1.143.1 according to both the
[GitHub releases API](https://github.com/microsoft/vscode/releases/tag/1.143.1) and
`https://update.code.visualstudio.com/api/releases/stable`. The v0.2.0 research and ADR 0005 call 1.142.0
the latest stable; that was true on 2026-10-20. For every API this note relies on, `vscode.d.ts` is the
same at 1.97.0 and 1.143.1 except `SecretStorage`, which gains `keys()` and a `readonly onDidChange`
([1.143.1 L8634-L8670](https://github.com/microsoft/vscode/blob/1.143.1/src/vscode-dts/vscode.d.ts#L8634-L8670),
[1.97.0 L8531-L8563](https://github.com/microsoft/vscode/blob/1.97.0/src/vscode-dts/vscode.d.ts#L8531-L8563)).
The other blocks compared were `Disposable`, `ExtensionContext`, `Memento`, `ConfigurationTarget`,
`WorkspaceConfiguration`, `ConfigurationChangeEvent`, `StatusBarItem` and `ExtensionKind`.

## Summary

- **VS Code prescribes the extension's outer shape, not its inner structure.** The docs define
  `activate`/`deactivate`, `context.subscriptions`, the storage options, setting scopes, Workspace Trust
  declarations and extension kinds. No page in `vscode-docs/api` says how to layer an extension, inject
  dependencies, or isolate logic from the `vscode` module. A search of the whole `api/` tree at
  `da21355` finds no mention of dependency injection or of mocking `vscode`. See
  [section 1](#1-vs-codes-guidance-on-extension-structure-and-lifecycle).
- **Microsoft's testing page covers integration tests only.** It calls its tests integration tests
  "because they go beyond unit tests that can run without a VS Code instance" and then documents only
  those. Two other pages say a little more: the bundling guide speaks of "the correct architectural
  layering", and the language-model guide recommends "designing your extension code in a modular way" so
  the deterministic parts can be unit tested. Neither says how. See [section 2](#2-vs-codes-testing-guidance).
- **Microsoft's own extensions use at least three different seams, and none is a VS Code-free core
  reached through parameters.** vscode-eslint puts the logic in a language server, a separate process
  that never imports `vscode`, and tests it with `node --test`. vscode-python-environments wraps `vscode`
  calls in module-level `*.apis.ts` functions, replaces the `vscode` module in unit tests and stubs the
  wrappers with sinon. The built-in git extension and vscode-pull-request-github construct classes by
  hand with constructor parameters (git passes `context.globalState` straight to `Model`) and run their
  tests inside the extension host. Of the extensions read, only the older vscode-python uses an IoC
  container (inversify), in code it labels "old activation code". Proxy Toggler's explicit parameters plus a hand-written fake of the
  `VscodeApi` slice, run under plain mocha, matches none of them exactly. It is closest to the PR
  extension's fakes, without the host. See [section 3](#3-how-first-party-extensions-separate-logic-from-the-api).
- **The skill's vocabulary mostly matches its sources, with three departures that matter for the
  review.** (1) It rejects "depth as a ratio of implementation lines to interface lines" and attributes
  that framing to Ousterhout. In the first-party material read here, Ousterhout frames depth as
  functionality against interface complexity and says "Size doesn't really matter that much"; no line
  ratio appears. (2) Its seam definition copies Feathers' sentence, then adds "the location at which a
  module's interface lives" and leaves out Feathers' enabling point. (3) Its testability principles
  ("the interface is the test surface", "designing for testability") go further than Ousterhout, who
  writes "It's not clear to me that designing for testability will produce the best design." See
  [section 4](#4-primary-sources-for-the-design-vocabulary).
- **Cockburn's ports are named by purpose, not by technology.** Ports and Adapters asks for interfaces
  "by purpose rather than by technology". `ARCHITECTURE.md` instead chooses "VS Code-shaped ports instead
  of custom wrappers" for the `VscodeApi` slice. Ousterhout's view supports the repo's side: mocking
  "just provides replacements for existing (typically immovable) interfaces". The other ports in the
  table (`HttpSettings`, `ProfilesSetting`, `ProxyNotices`) are named by purpose.
- **The repo follows the docs in most places and departs from their letter in four.** The status bar has
  two items, both on the right, created without an `id` or `name`. The UX guide says not to add more than
  one item "unless necessary" and to put global items on the left. Without an `id`, both items share the
  extension's identifier ([src/vscode/status-bar-controller.ts](../../src/vscode/status-bar-controller.ts)).
  The remote machine's record is key-value data kept in `globalStorageUri` through `node:fs`, where the
  guidance says to keep key-value data in `globalState` and shows `workspace.fs` for files
  ([src/vscode/file-memento.ts](../../src/vscode/file-memento.ts); ADR 0005 gives the reason). No
  notification offers "Do not show again". There is no `deactivate` export, which one Microsoft page
  says an extension "should" have and another says "can be removed".
- **The repo contradicts itself on activation.** `QUALITY_BASELINE.md` says to keep
  `"activationEvents": []` and to prefer a narrow event over `onStartupFinished`. `package.json` declares
  `onStartupFinished`, and `ARCHITECTURE.md` explains why. The VS Code docs say `onStartupFinished` "will
  not slow down VS Code startup".
- **The TypeScript handbook does not say whether to return result values or throw.** It defines
  discriminated unions, exhaustiveness checks with `never`, and `satisfies`, and stops there. For "define
  errors out of existence", Ousterhout's own notes are the source; they list "Return a special value" as
  one of four ways to report an exception that cannot be masked. See [section 5](#5-typescript-guidance-on-module-interfaces).

### How it applies here

- [src/extension.ts](../../src/extension.ts) exports `activate` only. This follows the anatomy page;
  the activation page's "should export `deactivate()`" is not met. Cleanup runs through
  `context.subscriptions` ([src/proxy-toggler.ts L80, L128, L131-L158, L178-L202](../../src/proxy-toggler.ts)),
  and every disposer registered there is synchronous, which matters because async ones are not awaited.
  `whenSettled` ([src/vscode/settle.ts](../../src/vscode/settle.ts)) registers a configuration listener
  outside `context.subscriptions` and disposes it itself once the setting goes quiet.
- [package.json L33-L35](../../package.json) declares `onStartupFinished`, as
  [ARCHITECTURE.md, "Activation after start-up"](../../ARCHITECTURE.md) explains.
  [QUALITY_BASELINE.md L67-L69](../../QUALITY_BASELINE.md) still says to keep `"activationEvents": []`
  and to prefer a narrower event. The repo contradicts itself here; the VS Code docs back the event
  that is declared.
- [src/core/proxy-settings-writer.ts L57-L69](../../src/core/proxy-settings-writer.ts) reads earlier
  values through `readUserSettings()` (`inspect().globalValue`) before writing. The `get()` merge order
  in `vscode.d.ts` is the reason this matters: `get()` would copy defaults and workspace values into user
  settings. [src/vscode/http-settings.ts L7-L11, L24-L30](../../src/vscode/http-settings.ts) reads
  `globalRemoteValue`, a field `vscode.d.ts` does not declare at either tag. That field is runtime
  behaviour with no API promise (v0.2.0 research row 4.5 marks it UNVERIFIED).
- Scopes: `proxyToggler.profiles` and `proxyToggler.showSwitchNotifications` are `application`
  ([package.json L85-L87, L122-L124](../../package.json)), which matches ADR 0002 and the scope
  definition. `proxyToggler.confirmBeforeToggle` ([package.json L80](../../package.json)) has no scope, so
  it is `window` and a workspace can set it, as ARCHITECTURE.md says. No setting uses `ignoreSync`, and
  no `globalState` key is passed to `setKeysForSync` (no match in `src/`), so every `globalState` key
  stays per machine and per VS Code Profile.
- Storage: the remote machine's record is key-value data. [src/vscode/file-memento.ts](../../src/vscode/file-memento.ts)
  keeps it as one JSON file per key under `globalStorageUri`, written with `node:fs`. The guidance says
  `globalState` for key-value data and shows `workspace.fs` for files, so this departs from its letter.
  [ADR 0005](../adr/0005-each-record-lives-with-its-settings.md) gives the reason the guidance does not
  cover: `globalState` is local even in the remote extension host. Since the extension is a
  `workspace` extension, `node:fs` runs on the remote machine, which is the intent. The same remote-guide
  warning about Node APIs applies to `node:os` in [src/vscode/proxy-side.ts L1, L40](../../src/vscode/proxy-side.ts)
  and `node:net`/`node:tls` in [src/core/test-connection.ts L1-L4](../../src/core/test-connection.ts).
- [src/core/keychain-service.ts L6](../../src/core/keychain-service.ts) types its port as
  `Pick<vscode.SecretStorage, 'get' | 'delete'>`. `keys()` exists only after 1.97.0, so the pinned
  `@types/vscode` 1.97.0 ([package.json L188](../../package.json)) keeps it out of reach, as intended.
- Workspace Trust: `untrustedWorkspaces.supported: true` ([package.json L36-L41](../../package.json)) fits
  the guide's test, since the extension reads no workspace files. The guide's own question ("settings
  that can be set by the workspace") is answered in ARCHITECTURE.md for `confirmBeforeToggle`.
- Status bar: [src/vscode/status-bar-controller.ts L32, L36](../../src/vscode/status-bar-controller.ts)
  creates two items (toggle and gear), both `StatusBarAlignment.Right`, both without `id` or `name`.
  Against the UX guide, that is two items where it says one "unless necessary", and the right side for
  what is arguably a window-wide state, where it puts such items on the left. Against `vscode.d.ts`, both
  items share the extension's identifier, so the status bar's hide menu cannot tell them apart (derived
  from source). The drift state uses `statusBarItem.warningBackground` (L66-L68), which the guide allows
  as a last resort.
- Notifications: no notification in `src/` offers "Do not show again" (no match). The repo avoids
  repetition by other means: one-time notices, a warning shown once per distinct set of hidden entries
  ([src/commands/profile-warning.ts L22-L27](../../src/commands/profile-warning.ts)), and success toasts
  off by default (`src/commands/proxy-feedback.ts` L9-L21, which `src/commands/proxy-change.ts` replaced).
- Quick input: [src/vscode/quick-pick.ts](../../src/vscode/quick-pick.ts) and
  [src/vscode/quick-input.ts](../../src/vscode/quick-input.ts) use `createQuickPick`/`createInputBox`. Their
  comments give the flexibility reasons `vscode.d.ts` asks for (open with an item focused; Back button;
  validation on accept). `askText` returns a `BACK` symbol, where Microsoft's sample throws
  `InputFlowAction.back`.

**Patterns observed.**

1. **Process seam** (eslint): the logic sits behind a protocol in another process. It is VS Code-free by
   construction and tested with `node --test`.
2. **Module-replacement seam** (python-environments, newer vscode-python): logic calls module-level
   wrappers; tests swap the `vscode` module at load time and stub wrapper exports. In Feathers' terms this
   is a link seam (section 4). The enabling point is the test bootstrap, not the production code.
3. **Constructor seam with VS Code-typed fakes** (PR extension, git): classes take `Memento`,
   `ExtensionContext` or API objects as constructor parameters. Tests pass fakes but still run inside the
   extension host. This is Feathers' object seam; the enabling point is where `activate` builds the
   objects.
4. **IoC container**: only in vscode-python's legacy path, which its own code marks for migration.

### How it applies here

- Proxy Toggler uses pattern 3, the object seam, with two differences. Its port types are narrower
  `Pick<…>` slices ([src/vscode/api.ts](../../src/vscode/api.ts), and `Memento` in
  [src/core/proxy-manager.ts L45](../../src/core/proxy-manager.ts)). And its unit tests run without the
  extension host, because only [src/extension.ts](../../src/extension.ts) loads `vscode` at runtime
  ([eslint.config.mjs](../../eslint.config.mjs), `no-restricted-imports` with `allowTypeImports`). The

- [src/core/proxy-manager.ts L87-L96](../../src/core/proxy-manager.ts) takes `globalState` and `records`
  as constructor parameters, as git's `Model` takes `context.globalState`.
- The `VscodeApi` port has two adapters, the `vscode` module and
  [tests/support/fake-vscode.ts](../../tests/support/fake-vscode.ts) (used in 19 test files). By the
  skill's rule that makes it a real seam. Microsoft's extensions do not build a whole-API fake of this
  kind: python-environments mocks namespaces with ts-mockito, and the PR extension fakes individual

- The test surface in practice: 13 test files construct the whole extension through

- No Microsoft extension read here keeps I/O-free logic in a folder enforced by lint the way `src/core`

  compile time, but the port vocabulary of the core (`Pick<vscode.Memento, …>`) comes from the outside
  technology. Cockburn's rule is about code; whether type vocabulary counts is a judgement the review
  will have to make.
- **Primary and secondary sides.** In Cockburn's terms, VS Code commands, configuration events and
  window focus are primary (driving) adapters wired in [src/proxy-toggler.ts L131-L202](../../src/proxy-toggler.ts).
  `http.*` settings, `proxyToggler.profiles`, `globalState`, the file record and `SecretStorage` are

  Ousterhout's measure is functionality per unit of interface complexity, not method count. His §6.5
  question "What is the simplest interface that will cover all my current needs?" (p. 44) is the
