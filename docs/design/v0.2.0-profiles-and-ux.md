# v0.2.0 Profiles & UX: design decisions

Agreed in a grilling session on 2026-10-20 and 2026-10-21: 87 questions over eleven rounds, with two
adversarial review passes, two research passes and a lab check over the decisions in between. Terms follow
[GLOSSARY.md](../../GLOSSARY.md). The hard-to-reverse decisions have ADRs:
[0001](../adr/0001-copy-not-move-migration.md),
[0002](../adr/0002-profiles-in-an-application-scoped-setting.md),
[0003](../adr/0003-no-stored-proxy-credentials.md),
[0004](../adr/0004-focused-window-acts-on-outside-changes.md) and
[0005](../adr/0005-each-record-lives-with-its-settings.md). The question numbers in brackets trace
each decision back to the session. [v0.2.0-research.md](v0.2.0-research.md) fact-checks the design
and weighs its value to users.

## Model

- Once at least one profile exists, exactly one profile is current, and it survives reloads. The
  "last-used profile" of #8 and #37 is the current profile. [Q2]
- The toggle turns the current profile on, writing `http.proxy`, `http.proxyStrictSSL` and
  `http.noProxy`, or off, clearing them. Picking a profile in the switcher makes it current and
  turns it on. [Q2]
- On/off and the current profile are Proxy Toggler's record. Local settings keep theirs per VS Code
  Profile in `globalState`; a remote machine's own settings keep theirs on that machine. Profiles
  themselves are shared by every VS Code Profile. [Q9, Q81, ADR 0005]
- Off means Proxy Toggler sets no proxy, and the Off tooltip says only that. What VS Code then uses
  is to be measured in the proxy lab: the source says direct, apart from `HTTP(S)_PROXY`, until VS
  Code restarts, and a system or PAC proxy only after that. A Direct entry waits for those
  measurements. [Q63, Q74, research B4]

## Supported VS Code

- The minimum VS Code version rises from 1.91 to 1.97, a behavior change the CHANGELOG records. On
  1.91 the window ignores an `http.proxy` that holds `user:pass@`, and extensions get no Basic
  sign-in dialog. Before 1.97 no setting says which proxy settings the remote side of a WSL or
  container window uses (`http.useLocalProxyConfiguration`). CI's oldest test run moves to 1.97.0.
  [Q73, Q82, research A3, B3, remote 5.1-5.4]

## Profiles and storage

- A profile is a name, a proxy URL, a strict SSL choice and a bypass list. It holds no credentials.
  The proxy URL may use `http`, `https`, `socks` or `socks5`. `socks4a` and `socks5h` are refused
  because the VS Code window rejects them, and `socks4` because the window and extensions resolve
  host names differently with it. [Q3, Q8, Q69, Q85]
- Profiles live in the application-scoped setting `proxyToggler.profiles`: shared by every VS Code
  Profile, editable in the Default profile's settings.json ("Preferences: Open Application Settings
  (JSON)"), never read from workspace files, and synced by Settings Sync. The name identifies a
  profile. [Q9, ADR 0002, research S10]
- Strict SSL stays per profile. The UI says that only VS Code's command line and some built-in
  extensions honor it, and nothing ever suggests turning it off. [Q30]
- New profiles start with an empty bypass list: VS Code always sends loopback addresses direct, and
  any non-empty list makes VS Code ignore the `NO_PROXY` environment variable. The bypass-list hint
  says both. Migrated profiles keep their lists. [Q44, Q72, research B2]
- `*.` patterns stay accepted, but prompts and examples suggest `.example.com`, and the hint says
  that only exact host names and `.` domains work for all of VS Code. [Q56]
- Names are trimmed, non-empty, at most 30 characters and unique ignoring case. The default name is
  the proxy host, shortened with "…" so that the name with any " (n)" suffix fits in 30 characters;
  n counts up from 2. [Q16, Q34]
- The first entry in the setting with a name owns that name, valid or not; later entries with the
  same name are hidden duplicates. Add, rename and default names skip every name an entry holds.
  [Q54]
- Hand edits and synced changes are re-read and checked like UI input. Invalid entries and
  duplicates stay out of the switcher, and one warning names them: once per distinct set of
  flagged entries, with the dismissal remembered per VS Code Profile until that set changes. Its
  "Open Settings" action opens the application settings file. [Q25, Q66, research S10]
- A save from the UI replaces or removes only the entry it changes, keeping invalid entries,
  duplicates and unknown fields. The schema allows extra properties. [Q39]

## Matching, reconciliation and drift

- VS Code's settings match a profile when they carry the same proxy URL after parsing (scheme, host
  and port, with an omitted port counting as the default; ignoring `user:pass@`, letter case and a
  trailing `/`), the same strict SSL (VS Code's default counts as on) and the same set of bypass
  patterns, in any order and ignoring case. [Q29, Q31, Q53]
- Every window reconciles its own record at activation and whenever `http.*` or
  `proxyToggler.profiles` changes, once the settings settle. Settings cleared: off. Settings that
  match a profile: that profile becomes current and on, and the current profile wins a tie. Both
  happen silently. [Q10, Q32, Q51]
- Drift: while at least one profile exists, VS Code's settings carry a proxy that matches no
  profile. Drift never changes the record. [Q10]
- Only the focused window acts on outside changes: it re-applies, and shows the invalid-entry
  warning and one-time notices. Other windows update their record silently and redraw. A window that
  makes a change treats its own change event as done. Notification buttons re-check the state when
  clicked. [Q33, Q51, ADR 0004]
- An outside edit to the remembered current profile is applied by the focused window, whether it
  was seen live or first found at activation, when the record is on and the settings still match the
  old values. While the proxy is on, the remembered values change only when that apply succeeds. A
  profile that is current only through the fallback is never re-applied. [Q25, Q67]
- When the current profile's name disappears, through a rename, delete, typo or sync, the profile
  with its remembered values is current, otherwise the first profile alphabetically. This fallback
  is computed when read and never saved. The remembered profile changes only through UI actions,
  valid edits to it, or a match found by reconciliation. [Q26, Q35]
- When the current profile disappears outside the UI while on, `http.*` is left alone and drift
  shows; fixing the entry ends the drift. [Q45]
- Each window writes only the record of the settings it manages. [Q62, Q81, ADR 0005]

## Drift display

- The toggle keeps its text, which shows the record, but its icon becomes `$(warning)`, the signal
  that works in every theme. It gets the warning background where the theme has one (High Contrast
  Dark has none), and its tooltip and screen-reader label say "VS Code uses a proxy that matches no
  profile". The toggle still acts on the record. [Q28, Q37, Q61, research V4]
- There is no drift notification; the toggle alone signals drift. [Q70, research: every surveyed
  tool signals drift passively]
- While drift lasts, the switcher adds "Save Current Settings as Profile…", plus "Re-apply
  <current>" while the record is on or "Turn Proxy Off" while it is off, and the Command Palette
  offers Turn Proxy Off. For values a profile cannot hold, the save entry names them instead of
  saving. [Q10, Q28, Q36, Q44, Q70]
- With no profiles there is no drift: the not-configured tooltip and label say VS Code already uses
  a proxy, and a click starts setup from it. [Q28]
- When a settings write fails partway, the window that failed shows only the write error. [Q48]

## Migration from 0.1.x

- Copy, never move: v0.2.0 never writes or deletes `proxyToggler.savedProxy`, so a downgrade still
  works, and `proxyToggler.state` keeps meaning on/off. [Q5, Q17, ADR 0001]
- Each VS Code Profile migrates its own `savedProxy` at its first v0.2.0 activation, adding a
  profile unless a profile the switcher shows already has the same values. [Q24, Q54]
- A marker in each VS Code Profile records the migrated values. It is written only after a later,
  settled read shows the profile; until then every activation retries. If `savedProxy` changes
  later, through a downgrade or a 0.1.x window still open, the new values migrate too. [Q40, Q46]
- A VS Code Profile with no current profile makes the migrated profile, or the existing profile
  with the same values, current without turning it on. [Q52]
- Every activation deletes the two 0.1.x credential secrets if they exist, in whichever window finds
  them. A notice appears once, only when one was found, in the next focused window of that VS Code
  Profile (ADR 0004), and a failed delete never fails migration. [Q8, Q41, Q79, ADR 0003]

## Credentials

- VS Code's own login dialog handles proxy sign-in; profiles hold no credentials. [Q8, ADR 0003]
- `user:pass@` in `http.proxy` is ignored for matching and stripped from everything shown or
  remembered. Before Proxy Toggler first overwrites or clears it, a one-time notice says the
  credentials will be removed. VS Code's dialog then answers for VS Code's own requests and for
  extensions' HTTPS requests. Extensions' plain `http://` requests through a Basic-auth proxy fail,
  because VS Code never asks for those. [Q31, Q73, research A4]

## Status bar and commands

- The profile name shows only when two or more profiles exist: "Proxy: Work" when on, "Proxy: OFF"
  when off. With one profile the text stays "Proxy: ON" or "Proxy: OFF". The tooltip names the
  current profile, and screen-reader labels always include it. [Q13]
- The words are on/off and turn on/turn off. Command titles become "Turn Proxy On" and "Turn Proxy
  Off"; command IDs do not change. [Q12]
- `proxyToggler.confirmBeforeToggle` guards only the toggle item and the Toggle command. [Q27]
- Success toasts are off by default. With `proxyToggler.showSwitchNotifications` on, turning on,
  turning off, switching (including from a keybinding) and deleting show a short toast without
  buttons that names the profile, which screen readers announce. Edit saves and reconciliation never
  show one. [Q38, Q71]

## Switcher

- The gear's Quick Pick lists the profiles first, alphabetically, with the current one checked and
  each proxy URL as its description. Then come Turn Proxy On/Off, Add Profile…, Edit Profile…,
  Delete Profile… and Extension Settings. [Q14]
- It opens with the current profile focused, so Enter keeps it, or turns it on when the proxy is
  off. [Q59]
- The palette command "Proxy Toggler: Switch Profile…" opens the same Quick Pick.
  `proxyToggler.configure` adds the first profile when none exists and edits the current one
  otherwise. Edit and Delete ask which profile, with the current one preselected. [Q14]

## Add, edit and delete

- Every flow uses native multi-step QuickInput with a Back button; there is no webview. [Q6]
- Add Profile has two steps: the proxy URL, then the name. Strict SSL starts on and the bypass list
  starts empty. When no profile exists and VS Code's settings hold a proxy, setup starts from those
  values, with any `user:pass@` removed, the default port written out and no trailing `/`. [Q21,
  Q53, Q72]
- When setup from settings meets values a profile cannot hold, it names them and offers "Continue
  Without Them" and "Open Settings". Continuing warns that the profile will not match VS Code's
  settings, so turning it on replaces them. "Save Current Settings as Profile…" refuses outright.
  [Q65]
- After a save, a notification offers "Turn On", "Test Connection" and "Not Now". If no profile
  matched the settings before the save and the new one does, it becomes current and on instead,
  and only "Test Connection" is offered. A save while no profile is remembered makes the saved
  profile current. [Q21, Q32, Q52, Q64]
- Edit Profile lists the fields with their values (Name, Proxy URL, Strict SSL, Bypass list) plus
  "Test Connection…". Each pick edits one field and saves it, returning to the list until Escape.
  Saving the current profile while on re-applies it. A rename warns that keybindings using the old
  name stop working. [Q15, Q22, Q49]
- Delete asks for confirmation. Deleting the current profile first turns the proxy off if it was
  on, and the first remaining profile becomes current, off. Deleting the last profile returns to
  not configured. There is no Duplicate action. [Q15, Q76]

## Test connection

- The test is optional and advisory: it never blocks saving, the URL is stored nowhere, it is
  prefilled with `https://marketplace.visualstudio.com`, and results are shown once and never
  logged. [Q7]
- Mechanism: `net.connect` to the proxy, or `tls.connect` for an `https://` proxy (with no
  `servername` for an IP address), a hand-written `CONNECT host:443`, TLS to the target over that
  socket, then `HEAD /`. `http://` targets go through the proxy without `CONNECT`. [Q23, Q47, Q57]
- For a `socks` proxy the test runs nothing and says it covers only HTTP and HTTPS proxies. [Q69]
- Verdicts: for an `https://` target any HTTP response passes; for an `http://` target 2xx and 3xx
  pass, and other statuses warn that the proxy may have sent them. A 407 warns that the proxy asks
  for sign-in. An unreachable proxy (refused, DNS, 10-second timeout) fails, and a refused tunnel
  fails with its status. [Q23, Q58]
- Certificates are checked against Node's built-in roots only, by passing `ca: tls.rootCertificates`
  on both TLS connections. An untrusted or self-signed issuer is a warning that names the issuer and
  says that the VS Code window and, by default, extensions accept it if the OS trusts that
  authority, while VS Code's command line does not; it links to the README's section on trusting a
  company's certificate authority. A name mismatch or a certificate outside its validity dates
  fails. Node skips those two checks when the chain fails, so the test runs them itself on its
  diagnostic connection. Nothing suggests turning strict SSL off. [Q42, Q57, Q75, research C3, C4,
  N3]
- The test is skipped only when both the VS Code window and extensions send the target direct;
  otherwise it runs and says which side bypasses the target. With `http.proxySupport: "off"`, the
  result says that extensions ignore VS Code's proxy settings. [Q55, Q63]
- In a remote window the test runs on the remote side and says where it ran: the remote's host name,
  or its type for containers. When that side uses this computer's proxy settings, the result also
  says that the VS Code window connects from this computer and was not tested. [Q81]

## Documentation

The README covers:

- proxy sign-in, and why extensions' plain `http://` requests through a Basic-auth proxy fail;
- trusting a company's certificate authority: the window and, by default, extensions use the OS
  store (`http.systemCertificates`), while VS Code's command line needs `NODE_EXTRA_CA_CERTS`;
- Settings Sync for `http.*` and `proxyToggler.profiles`, with what each uploads,
  `settingsSync.ignoredSettings` and how to merge a migration conflict;
- that proxy settings are shared by all VS Code Profiles;
- keybinding snippets that pass a profile name to `proxyToggler.switchProfile`, with no default
  keybindings and a note that renames break them;
- bypass patterns that work for all of VS Code, why loopback always goes direct, and how a bypass
  list affects `NO_PROXY`;
- what "off" means, once the proxy lab has measured it;
- `http.proxySupport`;
- remote windows: installing Proxy Toggler on the remote (the Extensions view's "Install in …"
  button, or `remote.defaultExtensionsIfInstalledLocally`), which proxy settings each kind of remote
  uses, and giving a WSL or container remote its own proxy.

[Q11, Q18, Q43, Q49, Q56, Q63, Q68, Q72, Q73, Q74, Q75, Q81, Q83]

## Remote windows

- A remote window's toggle and switcher manage the proxy that the window's remote side uses. When
  the remote keeps its own proxy settings (SSH, Tunnels and remote containers by default), switching
  writes the remote machine's settings and leaves local windows alone. When it uses the local
  settings (WSL and local Dev Containers by default), switching works as in a local window. Either
  way the status bar says which side it shows, and the profiles are the same shared list. [Q68, Q80]
- Proxy Toggler keeps its default `workspace` kind, so in a remote window it runs on the remote
  machine and must be installed there. [Q81]
- Each window writes only the record of the settings it manages: local settings keep theirs in
  `globalState`, and a remote machine's own settings keep theirs in a file in the extension's
  `globalStorageUri` on that machine, shared by every window connected to it. [Q81, ADR 0005]
- The status bar labels a remote machine's own settings with its host name, or with the remote type
  for containers. [Q80, Q81]
- In WSL and local-container windows, the switcher offers "Use a Separate Proxy for This Remote",
  which writes `http.useLocalProxyConfiguration: false` to the remote machine, and "Use This
  Computer's Proxy Again" reverses it. Reversing also removes the remote machine's `http.*` values:
  while they remain, later writes land in the remote file and change nothing (lab check 2). When the
  current profile's proxy host is a loopback address, the action comes first, with a note that WSL's
  NAT mode cannot reach it. [Q83, Q84]
- Proxy Toggler pins every remote machine it manages: turning the proxy off there writes an
  explicit empty `http.proxy` instead of removing the key, and reconciliation in those windows
  trusts only values in the remote machine's own settings. At start-up VS Code briefly gives an
  SSH-style remote side this computer's proxy, until the local setting changes again, while a value
  in the remote machine's settings wins (lab checks 1 to 4). A lab check confirms that an empty
  value pins the remote side. [Q87]
- Before remote support is built, the proxy lab gains an SSH host container and checks, on VS Code
  1.97.0 and the latest release: whether an SSH window's extensions see the local `http.proxy`; the
  stale-key trap, where a write lands in the remote file because that file already has the key;
  whether `http.useLocalProxyConfiguration` applies without a reload; and whether change events
  reach every window connected to the same machine. WSL is checked by hand on Windows. Results go in
  TESTING.md, "Remote windows": all four behaviors were measured, and check 1 found the start-up
  leak that Q87 answers. [Q84]

## Out of scope for v0.2.0

- Later candidates, recorded in the roadmap: a Duplicate action, a Next Profile command, a Direct
  entry (after the Off measurements), a bypass-pattern tester, and an opt-in setting that applies
  the current profile to integrated terminals. [Q15, Q74, Q76, Q77]
