# v0.2.0 Profiles & UX: research

This note fact-checks [the v0.2.0 design](v0.2.0-profiles-and-ux.md), its [glossary](../../GLOSSARY.md)
and [ADRs](../adr/), compares it with the tools users already switch proxies with, and weighs whether each
element has real value to users. Four read-only research passes ran on 2026-10-20: one per question, and a fourth on remote
windows once they came into scope. Their findings make up the last four sections, unedited except for
heading levels.

Every claim cites its source. The sources are VS Code, Electron, Chromium, Node and `@vscode/proxy-agent`
source at tagged versions, official documentation, store listings and APIs, and first-party issue threads,
reviews and questions. The repository's proxy-lab results in [TESTING.md](../../TESTING.md) count as evidence
where they apply. Line numbers quoted for the design, glossary and ADRs refer to their 2026-10-20 versions.

## Summary

- **Facts.** 43 claims, checked against VS Code 1.91.0 (the minimum engine) and 1.142.0 (the latest stable):
  34 confirmed, 9 partly right, none wrong. The partly right ones change wording and implementation details.
  One changes behavior: clearing `http.proxy` while VS Code runs probably sends traffic direct until VS Code
  restarts, instead of through the system or PAC proxy. Two research passes found this in the source
  independently; nobody has measured it. See [Fact-check](#fact-check).
- **Precedent.** Ten of the twelve design areas follow common practice in browser proxy switchers
  (ZeroOmega/SwitchyOmega, FoxyProxy, SmartProxy, Proxy Switcher and Manager, Proxy Helper), JetBrains IDEs
  and VS Code proxy extensions. SwitchyOmega already matches outside settings to saved profiles and offers to
  save unknown ones. The design departs from common practice in four places: no stored credentials (VS Code
  gives extensions no sign-in hook), no Direct entry, no SOCKS, and leaving `http.*` alone when the current
  profile disappears. See [Precedent](#precedent).
- **User value.** STRONG evidence for multiple profiles, the status bar display, safe migration, no stored
  credentials and strict SSL per profile. MODERATE for the switcher, the test connection, bypass-list guidance
  and Settings Sync guidance. WEAK for the drift warning, reconciliation, notifications and keybinding docs.
  Leaving remote windows and SOCKS out of scope rates NEGATIVE: those users are a large share of the people who
  switch VS Code proxies. See [User value](#user-value).
- **Remote windows.** A fourth pass, after the maintainer chose to support remote windows (Q68),
  established where a remote window's settings writes land, where per-machine state can live and how
  the two kinds of remote differ. See [Remote windows](#remote-windows).
- **Scale.** The 13 VS Code extensions that switch VS Code's proxy have 19,411 installs and 17 reviews between
  them; the largest has about 11,000 installs. Browser switchers reach hundreds of thousands of users.

## What this means for the design

### Corrections made on 2026-10-20

These fix facts and wording. No decision changed.

| Finding | Correction | Evidence |
| --- | --- | --- |
| Loopback addresses always go direct, and the window also sends dotless hosts direct and honors CIDR ranges and globs | Glossary **Bypass pattern** names the loopback exception | Fact-check B1, B2 |
| Clearing `http.proxy` at runtime probably makes VS Code go direct until a restart | Glossary **Off** and the design's Model section no longer promise a fallback to a system, environment or PAC proxy | Fact-check B4; Precedent 4.1 |
| Extensions' plain `http://` requests never get VS Code's login dialog; on 1.91 their HTTPS requests don't either | ADR 0003's consequence on `user:pass@` | Fact-check A4 |
| VS Code reads application-scoped settings only from the Default profile's settings.json | The design names "Preferences: Open Application Settings (JSON)", and the invalid-entry warning opens that file | Fact-check S10 |
| `statusBarItem.warningBackground` is empty in High Contrast Dark | The design makes the `$(warning)` icon the drift signal | Fact-check V4 |
| The window and, by default, extensions trust the OS certificate store, but VS Code's command line does not; Node skips name and date checks when the chain fails | The test connection pins `ca: tls.rootCertificates`, runs the name and date checks itself, and words the untrusted-issuer warning accordingly | Fact-check C3, C4, N3 |
| VS Code fires the change event before `update()` resolves | ADR 0004: a window records its pending write before awaiting `update()` | Fact-check S12 |

### Notes on the rows that are not CONFIRMED

**S10: editable in settings.json (PARTLY).** An application-scoped setting is read only from the Default profile's
settings.json. A user in another VS Code Profile who runs "Preferences: Open User Settings (JSON)" edits a file
that VS Code ignores for this setting; the entry shows faded with "can only be set in the settings file from the
Default profile" (1.142 wording). The command that works is "Preferences: Open Application Settings (JSON)"
([preferences.contribution.ts@1.91.0 L124](https://github.com/microsoft/vscode/blob/1.91.0/src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts#L124)).
Why it matters: the README and the invalid-entry warning should point non-default-profile users at that command,
or their hand edits silently do nothing.

**A4: "1.92+ the dialog asks; 1.91 fails" (PARTLY).** The auth lookup runs only in the CONNECT agent
(`HttpsProxyAgent2`). It never runs for plain `http://` requests, which use `HttpProxyAgent`, so those get the
407 on every version. Global `fetch()` is not proxied before 1.96 (on 1.95 it is wrapped only for
`http.electronFetch`, default off). From 1.96 it is proxied, with the same Kerberos and Basic lookup.
Why it matters: the README's 1.91 caveat should say "HTTPS requests from extensions"; plain HTTP requests from
extensions through a Basic-auth proxy fail on every version once `user:pass@` is removed.

**C3: "always Node's built-in roots" (PARTLY).** By default, a raw `tls.connect` in the extension host uses Node's
default store: the bundled Mozilla roots plus `NODE_EXTRA_CA_CERTS`. If the user enabled
`http.experimental.systemCertificatesV2`, VS Code's patched `tls.connect` adds OS CAs whenever `ca` is not passed.
When the TLS runs over an already-connected tunnel socket, whether those CAs get added even depends on load timing
([v0.21.0 L462-L479](https://github.com/microsoft/vscode-proxy-agent/blob/v0.21.0/src/index.ts#L462-L479)).
Why it matters: pass `ca: tls.rootCertificates` on both TLS legs. That makes "always" true, makes the result
deterministic, and skips the patch ([v0.45.0 L647](https://github.com/microsoft/vscode-proxy-agent/blob/v0.45.0/src/index.ts#L647)).

**C4: "accepts it only if the OS trusts that authority" (PARTLY).** The window and Marketplace (Chromium) use the OS
trust store. Extensions' HTTPS adds OS CAs only while `http.systemCertificates` is `true` (the default), and
`NODE_EXTRA_CA_CERTS` adds CAs the OS may not trust. `code --install-extension` uses Node's roots only
(`rejectUnauthorized` without OS CAs), so an OS-trusted corporate CA still fails there.
Why it matters: word the warning as "the VS Code window and, by default, extensions accept it if the OS trusts it",
or drop the absolute "only".

**N3: identity and date checks when the chain fails (PARTLY).** Node 20.9.0 and 24.21.0 call `checkServerIdentity`
only when chain verification succeeded, and expose one `authorizationError`. Probe results on both runtimes:

| Server certificate | Client trusts the CA? | `authorizationError` | `checkServerIdentity` called? |
| --- | --- | --- | --- |
| valid, right name | no | `UNABLE_TO_VERIFY_LEAF_SIGNATURE` | no |
| valid, wrong name | no | `UNABLE_TO_VERIFY_LEAF_SIGNATURE` | no (a manual call returns `ERR_TLS_CERT_ALTNAME_INVALID`) |
| expired, right name | no | `UNABLE_TO_VERIFY_LEAF_SIGNATURE` | no |
| expired, right name | yes | `CERT_HAS_EXPIRED` | no |
| valid, wrong name | yes | `ERR_TLS_CERT_ALTNAME_INVALID` | yes |

Why it matters: the test has to run these checks itself. One way is to connect with `rejectUnauthorized: false`,
then call `tls.checkServerIdentity(host, socket.getPeerCertificate())` and compare `valid_from`/`valid_to` with the
clock. Use that only on this diagnostic socket: send nothing but `HEAD /`, and fail or warn whenever
`socket.authorized` is false. Without these checks, an expired or misnamed certificate from an untrusted issuer is
reported only as "untrusted issuer" (a warning), not as the failure the design requires.

**B1: bypass-pattern rule (PARTLY).** The statement is right for exact names and `.domain` patterns, but it leaves out
three behaviors:

- The window appends `<local>` to the bypass list. In Chromium that sends every dotless host (`http://intranet/`)
  direct. Extensions send dotless hosts through the proxy.
- Chromium's implicit set also goes direct with no pattern: `localhost`, `*.localhost`, `127.0.0.0/8`, `::1` and
  link-local addresses. The extension host sends only the four exact names in B2 direct.
- The window honors CIDR ranges and globs such as `192.168.1.*`; extensions never match them.

Electron's `ProxyConfig` docs say `<local>` means 127.0.0.1, ::1 and localhost; Chromium's source says dotless
hosts ([proxy_bypass_rules.cc@122 L27-L32](https://github.com/chromium/chromium/blob/122.0.6261.156/net/proxy_resolution/proxy_bypass_rules.cc#L27-L32)).
Why it matters: the test-skip rule ("skipped only when both the window and extensions send the target direct") and
the "which side bypasses" message must model `<local>` and the implicit rules, or they will mislabel dotless and
loopback-range targets.

**B3: `http.proxy` forms (PARTLY).** Omitted port, letter case and trailing slash behave as the Match rule assumes.
`user:pass@` does not:

- **1.91 window**: skips `setProxy` entirely while `http.proxy` contains `@`, so it keeps the previous proxy, or the
  system proxy if none was set
  ([windowImpl.ts@1.91.0 L971](https://github.com/microsoft/vscode/blob/1.91.0/src/vs/platform/windows/electron-main/windowImpl.ts#L971)).
- **1.142 window**: strips the credentials.
- **Extensions**: send the credentials on CONNECT (lab: TESTING.md L52-53).

Why it matters: on 1.91, a URL with credentials and a profile without them do not route the window the same way. A
"match" there can hide a window that uses a different proxy. That is one more reason to apply the stripped URL
promptly after the one-time notice.

**B4: what "off" falls back to (PARTLY).** When `http.proxy` becomes empty at runtime and no `HTTP(S)_PROXY`
variable is set, VS Code calls `session.setProxy({ proxyRules: '', proxyBypassRules, pacScript: '' })`. With no
`mode`, Electron uses `fixed_servers`, and Chromium turns empty `fixed_servers` into DIRECT. The extension host
resolves hosts without a configured proxy through the same session (`session.resolveProxy`) and caches the answer
per host. So after a toggle-off, both sides go direct, not to the system or PAC proxy, until VS Code restarts. The
same happens at startup if `http.noProxy` is set while `http.proxy` is empty. The lab's PAC probe uses a fresh
profile and never toggles off, so it does not cover this.
Why it matters: "what off means" in the README (Q63) should say that system and PAC proxies come back only after a
restart. Add a lab probe: start with `--proxy-pac-url`, enable, disable, search again.

**V4: warning background in high contrast (PARTLY).** The color is `null` in High Contrast Dark, and no outline
replaces it. There, only the `$(warning)` icon, the tooltip and the screen-reader label show drift. The same holds
for the "Not Configured" state.
Why it matters: keep the icon change as the primary signal, and don't describe the background as the cue in docs or
tests.

### Other findings worth knowing

- **`NO_PROXY` interplay (B2).** When `http.noProxy` is empty, both the window and the extension host fall back to
  the `NO_PROXY` environment variable. Any non-empty list, including the default `localhost,127.0.0.1`, makes both
  ignore it ([windowImpl.ts@1.91.0 L969-L970](https://github.com/microsoft/vscode/blob/1.91.0/src/vs/platform/windows/electron-main/windowImpl.ts#L969-L970),
  [proxy-agent v0.21.0 L163-L180](https://github.com/microsoft/vscode-proxy-agent/blob/v0.21.0/src/index.ts#L163-L180)).
  The "may be empty" choice therefore changes behavior for users who rely on `NO_PROXY`.
- **Own-change detection (S12).** `writeConfigurationValue` reloads the configuration, which fires the event,
  before the `update()` call returns. Record a pending write before awaiting `update()`, or the window will treat
  its own change as an outside one.
- **Credential-secret notice (S3).** Secrets are application-wide, so the deletion and the one-time notice happen in
  whichever window activates first, possibly an unfocused one. ADR 0004 says only the focused window shows one-time
  notices; gate the notice accordingly, or note the exception.
- **Remote windows (R1).** A remote window's `globalState` is the local VS Code Profile's record. If a remote window
  wrote it from remote-machine settings, it would overwrite local state. This supports the "remote window never
  writes the record" rule.
- **Outdated docs page.** The "Legacy proxy server support" section of the network docs still says
  `http.proxyStrictSSL` and `http.proxyAuthorization` are respected for extensions. The source and the lab
  contradict it, so don't cite it.

### Older repo docs that contradict these findings

- `specs/001-proxy-toggler/research.md` L21 ("Secrets can optionally sync across devices") and L970 ("Credentials
  are automatically synced via SecretStorage") are wrong; SecretStorage never syncs (S5).
- `research.md` L16-19, `README.md` L20, L45 and L116 say secrets are stored in the OS keychain (Keychain,
  Credential Manager, Secret Service). This is imprecise: VS Code encrypts each secret with Electron `safeStorage`
  and stores it in its own application storage; the OS keychain holds only the key
  ([secrets.ts@1.91.0 L93-L111](https://github.com/microsoft/vscode/blob/1.91.0/src/vs/platform/secrets/common/secrets.ts#L93-L111),
  [encryptionMainService.ts@1.91.0 L35](https://github.com/microsoft/vscode/blob/1.91.0/src/vs/platform/encryption/electron-main/encryptionMainService.ts#L35),
  [Electron safeStorage docs](https://github.com/electron/electron/blob/v29.4.0/docs/api/safe-storage.md#L1-L12)).
- `research.md` L283 says `http.noProxy` supports `*.example.com` and `192.168.1.*`. The extension host matches
  neither; only the window does (B1).
- `research.md` L287 calls `http.proxyAuthorization` deprecated; it is not deprecated at 1.91 or 1.142
  ([request.ts@1.142.0 L324-L329](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/platform/request/common/request.ts#L324-L329)).
- `research.md` L290 lists `http.systemProxy`. There is no such setting; the setting is `http.proxySupport`
  (`off`/`on`/`fallback`/`override`).
- `README.md` L128-129 ("Ensure user-level proxy settings aren't being overridden by workspace settings") is wrong:
  application-scoped `http.*` cannot be set in workspace settings (S9).
- `ARCHITECTURE.md` L132-134 says workspace `http.*` values are ignored in Restricted Mode. They are ignored in
  every workspace, trusted or not, because the settings are application-scoped.
- `specs/001-proxy-toggler/contracts/StatusBarController.contract.md` L386-396 relies on the tooltip for
  screen-reader context. With `accessibilityInformation` set, as the code does, the tooltip is not read (V3).
- `TESTING.md` L88-91 says a self-signed HTTPS proxy "behaved the same with either value"; L200-201 says the HTTPS
  proxy case "is not measured". The source settles it either way: the extension host never reads
  `http.proxyStrictSSL`.

### 4. Features these tools have that the design does not plan

#### 4.1 VS Code constraints behind the verdicts

- **One proxy.** `http.proxy` is a single string. Its pattern allows the `http`, `https`, `socks`, `socks4`,
  `socks4a`, `socks5` and `socks5h` schemes. The setting is application-scoped, or machine-scoped when the
  host proxy is not used
  ([request.ts](https://github.com/microsoft/vscode/blob/e9a9b7df5c0a265e18c6b355c3e88faea5960da5/src/vs/platform/request/common/request.ts#L338-L346)).
- **`http.noProxy` means two different things.**
  - The window joins the entries into Electron `proxyBypassRules` and appends `<local>`, so Chromium syntax
    applies there: wildcards, CIDR and `<local>`
    ([windowImpl.ts](https://github.com/microsoft/vscode/blob/e9a9b7df5c0a265e18c6b355c3e88faea5960da5/src/vs/platform/windows/electron-main/windowImpl.ts#L1233-L1243),
    [Chromium proxy.md](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md)).
  - Extensions go through vscode-proxy-agent. There, each entry is a domain suffix with an optional `:port`.
    A lone `*` bypasses everything, and localhost, 127.0.0.1 and ::1 always go direct
    ([index.ts](https://github.com/microsoft/vscode-proxy-agent/blob/0a693b53a83bd6fec0835cc27c943cef46d0e77b/src/index.ts#L311-L345),
    [shouldBypassProxy](https://github.com/microsoft/vscode-proxy-agent/blob/0a693b53a83bd6fec0835cc27c943cef46d0e77b/src/index.ts#L472-L490)).
- **PAC.** The window always passes `pacScript: ''`. PAC therefore reaches VS Code only through the OS settings
  or the `--proxy-pac-url` launch flag
  ([windowImpl.ts](https://github.com/microsoft/vscode/blob/e9a9b7df5c0a265e18c6b355c3e88faea5960da5/src/vs/platform/windows/electron-main/windowImpl.ts#L1242-L1243),
  [network docs](https://code.visualstudio.com/docs/setup/network)).
- **Extension proxy support.** `http.proxySupport` takes `off`, `on`, `fallback` or `override`, and the
  default is `override`
  ([request.ts](https://github.com/microsoft/vscode/blob/e9a9b7df5c0a265e18c6b355c3e88faea5960da5/src/vs/platform/request/common/request.ts#L372-L384)).
- **Status bar colors.** A status bar item's background can only be the error or the warning color
  ([vscode.d.ts](https://github.com/microsoft/vscode/blob/e9a9b7df5c0a265e18c6b355c3e88faea5960da5/src/vscode-dts/vscode.d.ts#L7610-L7622)).
- **globalState is not synced** unless the extension calls `setKeysForSync`
  ([vscode.d.ts](https://github.com/microsoft/vscode/blob/e9a9b7df5c0a265e18c6b355c3e88faea5960da5/src/vscode-dts/vscode.d.ts#L8445-L8457)).
- **Runtime clearing may not mean "system" (UNVERIFIED).** See the caveat in section 3 under Model.

### 5. Points worth a second look

- **Closest precedent.** SwitchyOmega and ZeroOmega (about 930k users together) already combine three of the
  design's ideas: matching outside settings to a saved profile, adopting the match silently, and offering an
  "(External Profile)" entry to save. Their code is a useful reference for Match edge cases (see 2C).
- **Departures from common practice.** The design departs in four places:
  - It stores no credentials. VS Code's lack of an authentication hook justifies this.
  - It has no Direct entry.
  - It defers SOCKS.
  - It leaves `http.*` alone when the current profile disappears, where SwitchyOmega falls back to System
    and FoxyProxy to Disable.
- **The meaning of "off" (UNVERIFIED).** Source reading suggests that clearing `http.proxy` (and
  `http.noProxy`) while VS Code runs makes the window go DIRECT until restart, instead of using the system or
  PAC proxy. Run it in the proxy lab before the README explains what "off" means.
- **Test connection.** The test design lines up with the VS Code-native precedents: Network Proxy Test's raw
  CONNECT with 10-second timeouts, and otak-proxy's own-socket CONNECT with a Node CA check.
- **No precedent found** for strict SSL per profile, focused-window arbitration, copy-not-move migration, or
  the first-entry-owns-name rules.

## User value

Date of research: 2026-10-20. Design under test: `docs/design/v0.2.0-profiles-and-ux.md` (67 decisions) and
`GLOSSARY.md`. Question: do real users need what the design proposes?

### How to read this

**Sources.** Only first-hand sources: GitHub issue threads and comments, store listings and their reviews,
Stack Overflow and Super User questions and answers, and one Hacker News comment. No blog summaries.

**Weight signals.** `r` = reactions on the issue, `c` = comments, `v` = votes, `views` = Stack Exchange view
count, `installs` = VS Code Marketplace install statistic, `users` = store user count, `★ (n)` = average rating
and number of ratings. All counts were read on 2026-10-20.

**Verdicts.**

- STRONG: several independent first-hand sources with real weight (dozens of reactions or votes, tens of
  thousands of views, or store-scale user counts) point the same way.
- MODERATE: several consistent first-hand sources with modest weight.
- WEAK: one or a few low-weight sources, or only indirect or analogous evidence.
- NONE: no first-hand evidence found.
- NEGATIVE: evidence that users would dislike the decision. For the two "left out of scope" rows, the verdict
  rates the decision to leave the feature out: NEGATIVE means users need the excluded feature.

**Limits.**

- VS Code-specific volume is small. The 13 VS Code extensions that toggle or switch VS Code's proxy have
  19,411 installs combined and 17 reviews in total. Browser proxy switchers (hundreds of thousands of users)
  are used as an analogue for what proxy-switching users value; they are not the same audience.
- Reddit could not be read: scripted requests returned HTTP 403, Firecrawl does not support reddit.com, and the
  browser pane blocked the site. The one Reddit item below is marked UNVERIFIED.
- `microsoft/vscode-discussions` returned no proxy threads, so GitHub Discussions add nothing here.
- Theme counts over store reviews are my keyword counts and are approximate.
- Two Marketplace reviews were excluded as probable self-reviews: the 2025-02-16 otak-proxy review (reviewer
  name matches the repository owner) and the RidersWeb review (posted by the publisher account).
- Chrome Web Store numbers come from the listing pages fetched through Firecrawl. I checked them against the
  listing text quoted back by the tool, not against a second source.

### Verdicts at a glance

- **STRONG:** multiple profiles, status bar display, safe migration, no stored credentials (relying on VS Code's
  login dialog), strict SSL per profile.
- **MODERATE:** the switcher with keyboard access, the test connection, bypass-list guidance, Settings Sync
  guidance.
- **WEAK:** drift detection and its warning, reconciliation across windows and VS Code Profiles, notifications,
  keybinding docs.
- **NONE:** no element.
- **NEGATIVE:** leaving remote windows out of scope, and leaving socks out of scope. In both cases the evidence
  shows users who need the excluded feature: they are a large share of the people who switch VS Code proxies.

#### Q6. Which proxy each side uses

**The ext host's lookup order.** At every version checked, the extension host's `@vscode/proxy-agent` decides in this order:

1. Loopback targets go direct.
2. `http.noProxy`, or `NO_PROXY` when `http.noProxy` is empty.
3. `http.proxy`.
4. `HTTPS_PROXY`/`HTTP_PROXY` read at extension-host start.
5. Only when host proxy is on: ask the local window's Electron session (`resolveProxy`, which covers system proxy, PAC and fixed rules). Otherwise go DIRECT.

### Notes that affect the design

#### Identity

- **No stable API exposes a machine identity.** `env.remoteName` gives only the remote's type.
- **The full authority is out of reach.** In the remote extension host it is available only through proposed API, and every URI there is rewritten to `file:`. A UI extension sees it only through a workspace-folder URI, which needs an open folder.
- **The authority is a weak identity anyway.** The same SSH host can appear as an alias or as hex JSON; a container's authority encodes a folder path, not the container.
- **`env.machineId` in the remote host is the client's.** Do not use it to identify the remote machine.
- **Usable options:**
  - Avoid needing an identity by keeping per-machine state on the machine itself: the remote `globalStorageUri`, or the machine-scoped settings themselves.
  - When a label is needed, use `os.hostname()`.

#### Storage

- **Client side, shared by every window:** `globalState` and `workspaceState` live on the client and are shared across local and remote windows of a VS Code Profile. `secrets` are client side and shared across all profiles.
  - A `globalState` "current profile" record written by an SSH window would overwrite the local window's record (research doc R1).
  - Credentials stored once locally are readable from every remote window. That is convenient, but the secret then travels to the remote extension host process.
- **On the remote machine:** `globalStorageUri` and `storageUri` are per remote server data directory. They are the natural place for per-machine state such as "last profile applied on this machine".

#### Where writes land

| Window | `http.*` scope | `update(…, Global)` lands in | Affects the window (Electron)? | Affects the remote extension host? | Synced? |
| --- | --- | --- | --- | --- | --- |
| Local | application | local Default-profile `settings.json` | yes | n/a | yes |
| WSL or local container (default), or `useLocalProxyConfiguration: true` | application | local Default-profile `settings.json`, **unless the remote file already contains the key** (trap 4.3) | yes | yes, used from the WSL or container network | yes |
| SSH, Tunnels or remote container (default), or `useLocalProxyConfiguration: false` | machine | remote `<server data>/data/Machine/settings.json` | **no** | yes | no |

- In SSH-like windows, neither extension host can read or change the local window's proxy through the configuration API. A profile applied there is per machine, and it also applies to every other window connected to that machine (7.1).
- In WSL windows by default, applying a `127.0.0.1` profile works for the window and breaks remote extensions in NAT mode (6.4). From 1.97, the fix is to write `http.useLocalProxyConfiguration: false` plus a remote `http.proxy`. Both writes are machine-scoped and land in the WSL machine settings (5.3).
- On 1.92–1.96 that option does not exist (`update()` throws), and the scope is fixed per remote type by the server flag.
- `proxyToggler.profiles` (application scope) reads the same everywhere and is written to the local file.

#### What a test connection measures, and from where

- **Remote extension host (the default for this manifest):**
  - A test through Node `http`/`https` or `fetch` uses that host's resolution (6.1–6.3) and leaves from the **remote machine's network**.
  - A raw `net.connect` to a proxy also measures reachability from the remote. `127.0.0.1` means the remote's loopback.
  - Such a test cannot observe the window's Electron path. In the WSL default, a test can fail even though the window works; in SSH, it can pass while the window uses a different, local proxy.
- **Local extension host:** if the extension instead ran locally (`["ui","workspace"]` installed locally), tests would leave from the local network. However, in SSH windows the extension still could not write the local `http.proxy`, and 1.92 extension hosts read the merged value, which there is the remote value.
- **What follows:** label test results with where they ran (`remoteName`, `os.hostname()`), and treat the window's own path as untestable from a remote window.

#### Worth a lab check before relying on it

1. **SSH window with `http.proxy` set only locally:** does `get('http.proxy')` in a workspace extension return `""` (source) or the local value (vscode#236242, network-proxy-test#11)?
2. **The stale-remote-key trap:** application scope, with `http.proxy` present in the remote `Machine/settings.json`.
3. **Live toggling of `http.useLocalProxyConfiguration`** without a reload, on 1.97 and later.
4. **Remote-file change events across two windows** on the same host.
5. **The Codespaces default** for `useHostProxy`.
6. **Chromium with `socks5h://`:** confirm `ERR_NO_SUPPORTED_PROXIES` rather than DIRECT.
